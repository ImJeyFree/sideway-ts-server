## 적용 순서와 검증 계획

1. RTSP (`include/RtspStreamer.h`, `src/RtspStreamer.cpp`): 세션 스레드 회수, PAUSE/PLAY 수명 관리, 바이너리 RTCP 프레임 분리, 요청 크기/시간/연결 수 제한, 실제 UDP 포트 협상. 합성 TS와 로컬 소켓으로 재생 재개·종료·혼합 프레임을 검증합니다.
2. HTTP/RTP (`src/HttpStreamer.cpp`, `src/RtpStreamer.cpp`, `include/WebDashboard.h`): 90kHz 시간 계산, 제한 있는 요청 파싱, 명시적 상태 POST, 일괄 상태 조회. 잘못된 입력·반복 POST·응답 상태를 검증합니다.
3. 설정 (`include/QualityConfig.h`): 값 검증, 임시 파일 후 교체, 저장 성공 후 메모리 반영, Player 설정 버전/적용 확인 계약. 저장 실패와 재로드를 검증합니다.
4. 코어 (`src/ChannelScanner.cpp`, `src/TsBroadcaster.cpp` 및 관련 헤더): 실패 복구, 최신 스캔 정보 복원, 재생 중 PAT/PMT 추적. 합성 테이블과 제어 로직 회귀 검사로 검증합니다.
5. 진단 (`src/EpgCollector.cpp`, `src/TunerCoreApi.cpp`): 테이블 수신 진단과 DLL 지원 기능/빌드 정보. 기존 ABI 함수를 유지합니다.
6. 배포 (`tools/Prepare-PublicRelease.ps1`, `CMakeLists.txt`, 테스트): 누락 파일 보완, 두 저장소 Release 빌드 및 회귀 검사, 소스 ZIP을 풀어 독립 빌드합니다.

## 적용한 구현

### RTSP와 RTP

- 클라이언트 스레드를 세션에 보관하고 종료 시 중단 요청 → 송출 스레드 회수 → 소켓 정리 → 세션 스레드 회수 순서를 적용했습니다. 정리 책임은 세션 스레드 한 곳에 있습니다.
- PAUSE 시 송출 스레드를 회수하고 구독자를 해제합니다. PLAY 재개는 새 구독자로 현재 방송부터 받으며 기존 joinable 스레드를 덮어쓰지 않습니다.
- TCP의 `$` 인터리빙 프레임과 텍스트 제어 요청을 분리합니다. Content-Length 본문을 소비한 뒤 다음 요청을 처리합니다.
- 세션 유휴 제한은 안내와 동일하게 60초, 불완전 메시지의 수신 제한은 5초, 송신 제한은 2초입니다. RTSP 연결은 최대 32개입니다.
- SETUP은 실제 바인딩한 연속 RTP/RTCP 포트를 반환합니다. TCP 인터리빙 채널 번호도 요청값을 반영합니다. 세션 ID와 SETUP 선행 여부를 검사합니다.
- RTCP 수신 프레임은 소비하지만 RTCP Sender Report 생성·수신 통계 해석은 구현하지 않았습니다. 모든 RTSP 클라이언트에 대한 완전한 규격 호환을 보장하지 않습니다.
- RTP 및 RTSP RTP 타임스탬프는 실제 송출 시점의 단조 시각을 90kHz로 변환합니다. 선택 방송 전송률을 고정 19.34 Mbps로 가정하지 않습니다.

### HTTP 요청과 상태 조회

- 공통 `WireProtocol.h`: 제어 헤더 8 KiB, 본문 16 KiB, 중복 헤더·비정상 Content-Length·Transfer-Encoding 거절. RTSP 바이너리 프레임을 포함한 수신 버퍼도 제한합니다.
- HTTP 연결 최대 64개, 전체 요청 수신 시간 5초. 스레드 내부 예외가 전체 프로세스로 전파되지 않게 처리했습니다.
- `/api/status`는 코어 상태를 한 번 조회하고 HTTP/UDP/RTP/RTSP 상태를 추가합니다. 코어 `status`에는 `channelName`, 공개 응답에는 `rtspClients`가 추가됩니다. 하드웨어 값은 실시간 관측값으로 완전한 동시점 측정은 아닙니다.
- 기존 `tune` 경로로 다른 물리 채널에 전환해도 공개 송출 버퍼를 비웁니다. 동일 방송에 Player가 추가 접속할 때는 기존 시청자의 버퍼를 비우지 않습니다.

### 채널 복구와 실시간 PID 갱신

- 코어 `ChannelSelection::Switch`는 장치 적용 실패와 채널 파일 저장 실패 모두에서 이전 방송 복구를 시도합니다. 복구 자체 실패도 구분해 메시지를 남깁니다.
- 재스캔 완료 후 기존 방송 ID가 새 목록에 있으면 새 PMT/PCR/ES PID 정보로 복원합니다. 취소 등으로 새 정보가 없으면 이전 정보를 사용합니다.
- 튜너 정지 → 주파수 변경 → EPG/서비스 필터 설정 → 수신 시작 순서로 바꾸어 수신 시작 직후 이전 필터를 사용하는 구간을 줄였습니다.
- `ProgramTracker`가 선택 서비스 PAT/PMT의 CRC·섹션 길이·연속 카운터를 검사합니다. 새 PMT가 완성되기 전에는 이전 PID 집합을 유지하고, 유효한 새 PMT가 오면 출력 필터·PAT 버전·구독 버퍼를 갱신합니다.
- 실시간 PID 갱신은 메모리 송출 필터에 반영합니다. 매 PMT 변경마다 채널 JSON을 디스크에 쓰지는 않습니다. 장치 재연결과 실제 방송 PID 변경은 별도 하드웨어 검증 대상입니다.
- Player TS에서 PSIP를 제외하는 기존 Android VLC 호환 처리는 유지합니다.

### 설정 저장과 적용 확인

- 허용 키, 문자열 값, 정수 범위를 검사합니다. 알 수 없는 키·소수형 스레드 수·음수 캐시 시간은 거절합니다.
- `avcodecThreads`: 0~64 정수. `networkCachingMs`: 100~10000 정수.
- 디인터레이스: `bob/yadif/blend/off`, 전송 방식: `tcp/udp`, 하드웨어 가속: `auto/on/off`.
- 임시 파일 쓰기·flush·close 확인 후 Windows 파일 교체를 수행하고, 성공한 경우에만 메모리 값과 revision을 갱신합니다. 실패 시 기존 값과 파일을 보존합니다.
- 기존 정상 설정 파일은 읽을 수 있으며 revision이 없으면 1로 취급합니다. 손상된 기존 파일은 초기 로드 시 덮어쓰지 않습니다.
- Player 적용 보고는 최근 5분, 최대 64개 clientId만 메모리에 보관합니다. 서버 재시작 시 보고 목록은 초기화됩니다.

## 변경·추가 API 사용법

변경용 POST에는 `X-TS-Action: 1`이 필요합니다. 이 헤더는 사용자 인증 수단이 아닙니다. 인증 없는 내부망 서버라는 기존 운영 조건은 동일합니다.

| 경로 | 메서드 | 입력·결과 |
|---|---|---|
| `/api/udp/enabled` | POST | `{"enabled":true}` 또는 `false` |
| `/api/rtp/enabled` | POST | 위와 동일 |
| `/api/rtsp/enabled` | POST | 위와 동일. false이면 기존 RTSP 연결도 종료 |
| `/api/tune?ch=82&qam=0` | POST | 기존 물리 채널 변경. 가능한 경우 저장 방송 ID 선택 API 권장 |
| `/api/config/quality` | GET | 기존 설정 필드와 `revision` |
| `/api/config/quality` | POST | 변경할 설정 필드만 전달. revision은 입력에서 제외 |
| `/api/config/quality/applied` | POST | `{"clientId":"player-1","revision":2}`. 최신 revision 적용 완료 보고 |
| `/api/config/quality/status` | GET | revision, scope, confirmation, clients |
| `/api/version` | GET | serverVersion, serverBuild, features, core |

기존 `/api/udp/toggle`, `/api/rtp/toggle`, `/api/rtsp/toggle` 경로도 POST와 명시적인 enabled 본문으로만 사용할 수 있습니다. 이전의 GET 호출은 405입니다. 단순 상태 반전 요청은 지원하지 않습니다.

```powershell
$baseUrl = 'http://localhost:8080'
$headers = @{ 'X-TS-Action' = '1' }
Invoke-RestMethod "$baseUrl/api/rtsp/enabled" -Method Post -Headers $headers `
    -ContentType 'application/json' -Body '{"enabled":true}'
Invoke-RestMethod "$baseUrl/api/config/quality" -Method Post -Headers $headers `
    -ContentType 'application/json' -Body '{"networkCachingMs":1500}'
Invoke-RestMethod "$baseUrl/api/version" | ConvertTo-Json -Depth 6
```

Player는 설정 GET → 로컬 디코더/재생 옵션 적용 → 성공한 revision을 POST 순서로 연동합니다. 실제 적용에 실패하면 보고하지 않습니다. 서버는 적용을 강제하거나 검증하지 않으며 `confirmation: "player_reported"`로 구분합니다. 오래된 revision은 409를 반환하므로 다시 조회해야 합니다. Android Player 소스는 이번 작업에서 수정하지 않았습니다.

## EPG 및 DLL 진단

- `/api/epg`의 `diagnostics`에 mgt/vct/stt/eit/ett 각각의 `seen`, `lastSeenUtc`를 추가했습니다. CRC가 정상인 테이블 관측을 의미하며 선택 서비스의 편성 수집 완료 여부와 다릅니다. 채널 전환 시 초기화합니다.
- `stc_query(...,"capabilities",...)`는 DLL version/build/abiVersion/features를 반환합니다. ABI v1과 기존 export 함수는 유지합니다.
- `/api/version`에서 구형 DLL이 capabilities를 지원하지 않으면 core는 null입니다. 날짜 대신 실행 중인 DLL의 기능을 확인할 수 있습니다. 빌드 식별값은 컴파일 날짜·시간이며 서명이나 재현 빌드 해시를 의미하지 않습니다.

## 배포 구성

- RTP/RTSP 소스·헤더, 품질 설정, 공통 파서, 새 테스트 및 본 문서를 소스 배포 목록에 추가했습니다.

## 검증 중 발견한 추가 경합과 수정

- 첫 네트워크 확장 검사에서 UDP 재생 이후 새 유휴 세션을 종료하는 과정이 CTest 시간 제한에 걸렸습니다. 단계별 진단 로그로 송출 종료가 아니라 막 연결된 세션의 handler 회수 대기임을 확인했습니다.
- 긴 blocking recv와 shutdown의 경합에 의존하지 않도록 250ms select 대기 후 종료 플래그를 확인합니다. 세션 유효 시간은 60초로 유지하며 메시지 조립은 5초 제한입니다.
- 이 수정 후 네트워크 회귀 검사 15회 연속 통과(17.80초). 임시 TRACE 출력은 최종 소스에서 제거했습니다.
- 공개 HTTP/로더 검사 3개, 비공개 코어 검사 3개와 실제 DLL ABI 검사도 통과했습니다. 최종 전체 검사와 최종 패키지 결과는 아래에서 구분합니다.

## 사용자가 확인할 실제 환경 항목

1. 방송 서버를 정상 종료한 뒤 검증용 EXE와 DLL을 함께 사용합니다. 기존 채널 JSON은 백업 후 경로를 지정해 재사용하세요.
2. RTSP 재생 → 일시정지 → 재생 반복과 앱 재접속, 송출 정지/시작, 서버 종료를 확인합니다.
3. 재스캔 뒤 같은 방송 복원, 수신 불가 채널 선택 시 이전 방송 복구를 확인합니다.
4. Android Player가 새 POST 제어 API와 설정 revision/적용 보고 계약을 사용하도록 연동합니다. 일반 VLC는 적용 보고 API를 호출하지 않습니다.
5. 실제 방송의 동적 PID 변경과 USB 튜너 드라이버 오류 복구는 합성 데이터 검사만으로 보장하지 않습니다.
